# 配置、提及与第三方模型

## 自定义 @

在「互动」开启「评论时添加 @ 提及」，再选择帖子作者、自定义用户或不提及。自定义需要同时填写昵称和数字用户 ID；昵称支持 `昵称` 和 `@昵称`，保存时统一去掉前缀。昵称和 ID 必须属于同一账号，插件不会按昵称自动搜索或确认身份。此设置影响帖子评论；评论回复仍通过平台 `reply_id/root_id` 指向来信。

0.10.2 根据用户提供的官方 App 选择用户后的评论标记生成提及：`<a data-user-id="12345678" href="https://api.xiaoheihe.cn/open_inapp/#heybox://%7B%22protocol_type%22%3A%22openUser%22%2C%22user_id%22%3A%2212345678%22%7D">@示例用户</a>`。作者模式从帖子作者数据读取 ID 与昵称；自定义模式使用 `mentionUserId` 与 `mentionName`。链接由宿主生成并放入 `text` 表单字段，昵称进行 HTML 转义，模型仍不能生成 HTML 或 @。

旧版只填昵称的配置仍能读取，历史保留；自定义 @ 缺少 ID 时会记录明确错误并停止该条评论发送，不再降级成普通文字。补齐 ID 并保存后对后续新帖子生效，不会重新发送旧评论。当前已验证标记与样本一致、提交编码保留原文；该样本是已显示评论中的标记，并非创建请求抓包，平台是否接受此标记并触发通知仍需真实账号联调。

## 第三方 API

「高级 → 模型来源」选择第三方 API，填写兼容 Chat Completions 的 Base URL、模型名和 API Key。例如 Base URL 为 `https://api.example.com/v1` 时，调用 `/v1/chat/completions`；完整端点也支持。远程地址使用 HTTPS，本机 localhost / 127.0.0.1 / ::1 可用 HTTP。只支持非流式文本输出，不提供工具或发送小黑盒 Cookie。

两种模型来源共用相同提示词与结果校验。帖子评论使用「通用人设与兴趣」，回复使用「回复人格」，空白回复人格沿用通用人格。人格放入 system 消息，帖子和评论作为不可信的 user 数据传入。模型只决定 send / skip 与正文；提及、额度、去重、冷却和平台发送均由宿主控制。提示词约束不能保证任意第三方模型完全遵守人格，需根据实际输出调整模型和设定。

API Key 保存在服务器配置文件，状态接口不返回密钥；表单留空保留已有密钥，显式点击清除可删除。第三方请求禁止跟随重定向，不自动重试；错误记录只保留本地错误说明及 HTTP 状态，不记录上游响应正文。

## 编辑配置文件

独立配置位于 `$DSH_HOME/heybox/config.json`，默认 `~/.dsh/heybox/config.json`，首次从旧 automation.json 自动迁移。文件权限 0600。密钥仅保存在该文件；浏览历史与发送记录仍位于 `automation.json`，不会写入 B 站目录。

可在「高级 → 配置文件」打开 JSON 快照，修改后点击「保存配置文件」。快照不包含已有 apiKey；省略该字段会保留密钥，`"apiKey": ""` 会清除。此操作会同步表单并覆盖尚未保存的表单修改。也可直接编辑服务器文件，建议停止当前任务后用临时文件加 rename 的方式原子替换；设置在下次调度读取，已计算的下一次运行时间仍沿用，界面保存设置会重新计算。

示例为增量配置，可通过编辑器提交：

```json
{
  "mentionAuthor": true,
  "mentionTarget": "custom",
  "mentionName": "示例用户",
  "mentionUserId": "12345678",
  "generationProvider": "external",
  "apiBaseUrl": "https://api.example.com/v1",
  "apiModel": "your-model",
  "persona": "喜欢游戏，简洁友好，有具体内容再评论。",
  "replyPersona": "先回应对方的问题，保持耐心，不编造经历。"
}
```

直接替换整个服务器文件时应在现有完整配置上修改，保留所需开关及密钥；文件缺失字段会使用默认值。未知字段、非法类型和无效地址会被拒绝，损坏配置会停止调度，修复后重启宿主。不要把带密钥的配置提交到 Git 或发给他人。

## 自定义调度（0.10.1）

「运行时段」提供不限时段、峰谷、峰底快捷方案，点击只更新表单，保存后生效。所有时间均可继续修改，时区可自定义。峰底预设为每天 00:00–06:00 的示例，请按模型供应商实际时段调整。

工作日、周末、节假日分别使用 valleyWindows、weekendWindows、holidayWindows，每类最多 10 段。界面用时间选择器编辑，无需计算分钟。配置文件仍使用分钟数组，例如 [[1350,315]] 表示 22:30–次日 05:15，[[0,1440]] 表示全天，[] 表示当天不运行。每个本地日期先判断日历类型，再应用该类型的时段；例如周五跨午夜时段的凌晨部分按周五规则判断，周六凌晨按周末规则判断。节假日优先，周末补班使用工作日规则。关闭时段限制会保留所有时间段。已有配置不会被自动替换成新预设。

界面将执行频率与允许运行时段分别说明：浏览页的「调度检查间隔」从本轮结束或跳过后计时，保存设置会重新计时；运行时段页决定到点能否开始。概览分别显示浏览与回复的下次检查时间，其中「下次浏览检查」，这个时间不保证开始刷帖，时间按浏览器本地时区显示，时段判定按配置的调度时区。时段外跳过后等待下一次检查，时段开启不会额外触发；较短时段可能被较长间隔错过。手动「立即执行一轮」也受时段限制。已开始的浏览可能在窗口外继续，评论在生成前后及发送前检查时段；回复仅在 replyFollowSchedule 开启时检查时段。


## 独立回复检查（0.10.4）

「互动 → 回复来信」可独立开启自动回复，不依赖定时浏览开关。开启后通常在下一次宿主调度检查（5 秒内）开始检查，随后从检查完成时起等待 `replyIntervalSeconds` 秒。默认 180 秒，可配置 30–86400 秒。更短间隔会增加平台请求量，尚未通过真实账号验证其长期稳定性。

- `autoReply`：回复任务开关，默认关闭。
- `replyIntervalSeconds`：回复检查间隔；界面修改该值会重新计算下次检查时间。
- `replyFollowSchedule`：默认关闭，即全天检查；开启后遵守浏览页所用的运行时段规则。关闭全局时段限制时仍为全天。
- `repliesPerRound`：每轮最多处理的来信数（1–10），模型决定跳过也占一个名额；实际发送另外受 `dailyReplies` 限制。

消息获取参考 WenfuRainbow/heybox 的轮询方式，使用 `/bbs/app/user/message?list_type=0`，不是服务端推送。优先使用明确的未读标记；明确已读的消息跳过。没有可识别已读状态时，只处理时间晚于本账号启用基线的消息，缺少有效时间则跳过。未读标记可能包含旧未读消息，所以首次开启仍可能处理旧未读来信。每轮最多查 100 条消息，大量积压不保证全部覆盖。

回复前仍核对帖子、父评论和账号关系，使用回复人格（留空沿用通用人格），模型可决定跳过。处理结果和基线按账号持久化；已处理、明确拒绝或发送结果未知的来信不会自动重发。重启保留基线和去重记录，关闭后重新开启会更新无已读标记消息的时间基线。

浏览和回复有独立的到期时间，但共用执行锁与发送冷却，按到期先后串行执行。当前浏览、模型生成及发送冷却都会延迟回复；这不是实时推送或固定延迟承诺。「立即执行一轮」仍用于浏览。「停止全部任务」同时关闭两项开关，并取消尚未提交的生成与发送。

连续失败按检查间隔的 2、4、8、16、32 倍延长等待，成功后恢复正常间隔。登录失效或要求人机验证时暂停回复检查，概览展示原因；完成验证并重新登录、更新凭据后恢复。也可处理问题后关闭自动回复、保存，再开启保存。暂停与错误不会删除浏览历史或已发送记录。

升级后原有 autoReply 开关会保留，默认改为全天独立检查；需要保持原运行时段限制的用户请开启 replyFollowSchedule。新增调度状态仅写入小黑盒自己的 automation.json，不操作 B 站插件文件。
