# 配置、提及与第三方模型

## 自定义 @

在「互动」开启「评论时添加 @ 提及」，再选择帖子作者、自定义用户或不提及。自定义默认需要同时填写昵称和数字用户 ID；昵称支持 `昵称` 和 `@昵称`，保存时统一去掉前缀。昵称和 ID 必须属于同一账号，插件不会按昵称自动搜索或确认身份。此设置影响帖子评论；评论回复仍通过平台 `reply_id/root_id` 指向来信。

0.10.2 根据用户提供的官方 App 选择用户后的评论标记生成提及：`<a data-user-id="12345678" href="https://api.xiaoheihe.cn/open_inapp/#heybox://%7B%22protocol_type%22%3A%22openUser%22%2C%22user_id%22%3A%2212345678%22%7D">@示例用户</a>`。作者模式从帖子作者数据读取 ID 与昵称；自定义模式使用 `mentionUserId` 与 `mentionName`。链接由宿主生成并放入 `text` 表单字段，昵称进行 HTML 转义，模型仍不能生成 HTML 或 @。

旧版只填昵称的配置仍能读取，历史保留；默认自定义 @ 缺少 ID 时会记录明确错误并停止该条评论发送。0.10.7 新增 `mentionPlainTextFallback`（布尔值，默认 `false`），对应「缺少 ID 时允许纯文本 @」开关：显式开启后，没有 ID 时生成普通 `@昵称 正文`；这不绑定用户，不能保证通知对方。有 ID 时仍生成上述链接，不会降级。此选项不影响作者模式、不提及模式或评论回复；升级不会自动开启，也不会重新发送已处理的旧评论。

补齐 ID 并保存后对后续发送生效。当前已验证标记与样本一致、提交编码保留原文；该样本是已显示评论中的标记，并非创建请求抓包，平台是否接受此标记并触发通知仍需真实账号联调。评论创建接口的 Workshop v15 `_rnd` 签名自 0.10.5 已内置，评论和回复共用；无需运行旧脚本重复修改插件文件。

## 第三方 API

「高级 → 模型来源」选择第三方 API，填写兼容 Chat Completions 的 Base URL、模型名和 API Key。例如 Base URL 为 `https://api.example.com/v1` 时，调用 `/v1/chat/completions`；完整端点也支持。远程地址使用 HTTPS，本机 localhost / 127.0.0.1 / ::1 可用 HTTP。只支持非流式文本输出，不提供工具或发送小黑盒 Cookie。

两种模型来源共用相同提示词与结果校验。帖子评论使用「通用人设与兴趣」，回复使用「回复人格」，空白回复人格沿用通用人格。人格放入 system 消息，帖子和评论作为不可信的 user 数据传入。模型只决定 send / skip 与正文；提及、额度、去重、冷却和平台发送均由宿主控制。提示词约束不能保证任意第三方模型完全遵守人格，需根据实际输出调整模型和设定。

API Key 保存在服务器配置文件，状态接口不返回密钥；表单留空保留已有密钥，显式点击清除可删除。第三方请求禁止跟随重定向，不自动重试；错误记录只保留本地错误说明及 HTTP 状态，不记录上游响应正文。

## 编辑配置文件

独立配置位于 `$DSH_HOME/heybox/config.json`，默认 `~/.dsh/heybox/config.json`，首次从旧 automation.json 自动迁移。文件权限 0600。密钥仅保存在该文件；浏览历史与发送记录仍位于 `automation.json`，不会写入 B 站目录。

可在「高级 → 配置文件」打开 JSON 快照，修改后点击「保存配置文件」。快照不包含已有 apiKey；省略该字段会保留密钥，`"apiKey": ""` 会清除。此操作会同步表单并覆盖尚未保存的表单修改。也可直接编辑服务器文件，建议停止当前任务后用临时文件加 rename 的方式原子替换；设置在下次调度读取，已计算的下一次运行时间仍沿用，界面保存设置会重新计算。

示例为增量配置，可通过编辑器提交：

```json
{
  "mentionAuthor": true,
  "mentionTarget": "custom",
  "mentionName": "示例用户",
  "mentionUserId": "12345678",
  "generationProvider": "external",
  "apiBaseUrl": "https://api.example.com/v1",
  "apiModel": "your-model",
  "persona": "喜欢游戏，简洁友好，有具体内容再评论。",
  "replyPersona": "先回应对方的问题，保持耐心，不编造经历。"
}
```

直接替换整个服务器文件时应在现有完整配置上修改，保留所需开关及密钥；文件缺失字段会使用默认值。未知字段、非法类型和无效地址会被拒绝，损坏配置会停止调度，修复后重启宿主。不要把带密钥的配置提交到 Git 或发给他人。

## 自定义调度（0.10.1）

「运行时段」提供不限时段、峰谷、峰底快捷方案，点击只更新表单，保存后生效。所有时间均可继续修改，时区可自定义。峰底预设为每天 00:00–06:00 的示例，请按模型供应商实际时段调整。

工作日、周末、节假日分别使用 valleyWindows、weekendWindows、holidayWindows，每类最多 10 段。界面用时间选择器编辑，无需计算分钟。配置文件仍使用分钟数组，例如 [[1350,315]] 表示 22:30–次日 05:15，[[0,1440]] 表示全天，[] 表示当天不运行。每个本地日期先判断日历类型，再应用该类型的时段；例如周五跨午夜时段的凌晨部分按周五规则判断，周六凌晨按周末规则判断。节假日优先，周末补班使用工作日规则。关闭时段限制会保留所有时间段。已有配置不会被自动替换成新预设。

界面将执行频率与允许运行时段分别说明：浏览页的「调度检查间隔」从本轮结束或跳过后计时，保存设置会重新计时；运行时段页决定到点能否开始。概览分别显示浏览与回复的下次检查时间，其中「下次浏览检查」，这个时间不保证开始刷帖，时间按浏览器本地时区显示，时段判定按配置的调度时区。时段外跳过后等待下一次检查，时段开启不会额外触发；较短时段可能被较长间隔错过。手动「立即执行一轮」也受时段限制。已开始的浏览可能在窗口外继续，评论在生成前后及发送前检查时段；回复仅在 replyFollowSchedule 开启时检查时段。


## 独立回复检查（0.10.4）

「互动 → 回复来信」可独立开启自动回复，不依赖定时浏览开关。开启后通常在下一次宿主调度检查（5 秒内）开始检查，随后从检查完成时起等待 `replyIntervalSeconds` 秒。默认 180 秒，可配置 30–86400 秒。更短间隔会增加平台请求量，尚未通过真实账号验证其长期稳定性。

- `autoReply`：回复任务开关，默认关闭。
- `replyIntervalSeconds`：回复检查间隔；界面修改该值会重新计算下次检查时间。
- `replyFollowSchedule`：默认关闭，即全天检查；开启后遵守浏览页所用的运行时段规则。关闭全局时段限制时仍为全天。
- `repliesPerRound`：每轮最多处理的来信数（1–10），模型决定跳过也占一个名额；实际发送另外受 `dailyReplies` 限制。

消息获取参考 WenfuRainbow/heybox 的轮询方式，使用 `/bbs/app/user/message?list_type=0`，不是服务端推送。优先使用明确的未读标记；明确已读的消息跳过。没有可识别已读状态时，只处理时间晚于本账号启用基线的消息，缺少有效时间则跳过。未读标记可能包含旧未读消息，所以首次开启仍可能处理旧未读来信。每轮最多查 100 条消息，大量积压不保证全部覆盖。

回复前仍核对帖子、父评论和账号关系，使用回复人格（留空沿用通用人格），模型可决定跳过。处理结果和基线按账号持久化；0.10.6 起候选来信先入队，未处理完和可重试的失败留到下轮，详见下节。重启保留基线、队列和去重记录，关闭后重新开启会更新新发现的无已读标记消息的时间基线，不删除已有队列。

浏览和回复有独立的到期时间，但共用执行锁与发送冷却，按到期先后串行执行。当前浏览、模型生成及发送冷却都会延迟回复；这不是实时推送或固定延迟承诺。「立即执行一轮」仍用于浏览。「停止全部任务」同时关闭浏览、回复和发帖三项开关，并取消尚未提交的生成与发送。

消息获取失败或登录、验证、限流等检查错误按检查间隔的 2、4、8、16、32 倍延长等待，成功后恢复正常间隔。单条生成或普通明确拒绝保留到下一正常检查，不阻塞其他来信。登录失效或要求人机验证时暂停回复检查，概览展示原因；完成验证并重新登录、更新凭据后恢复。也可处理问题后关闭自动回复、保存，再开启保存。暂停与错误不会删除队列、浏览历史或已发送记录。

升级后原有 autoReply 开关会保留，默认改为全天独立检查；需要保持原运行时段限制的用户请开启 replyFollowSchedule。新增调度状态仅写入小黑盒自己的 automation.json，不操作 B 站插件文件。


## 评论发送诊断（0.10.5）

「评论记录」中的失败记录新增平台响应：HTTP 状态、业务状态（例如 failed）和消息（例如“缺失参数”）。最近动态同步显示上述原因。文本会过滤当前账号凭据、配置密钥及常见凭据字段，并限制长度，不保存整份平台响应。旧记录缺失的原因无法补回。

评论与回复统一使用新版网页评论创建参数（web_version=3.0）和逐请求生成的 _rnd 签名。附加签名使用公开网页协议常量，不是个人 API Key；它不会替代 Cookie，也不会发送给第三方。此修改仅针对评论创建接口，不推断其他写接口也使用相同规则。

升级保持发送记录、额度和去重；旧版未入队的 rejected / unknown 记录不会自动重试。0.10.6 起新入队回复的 rejected 会重试，帖子评论仍保持原有去重。网络异常或非成功 HTTP 状态仍可能无法确定是否写入，不自动重发；HTTP 200 且业务状态明确失败则记录 rejected。

## 失败与积压回复队列（0.10.6）

每轮先将最近 100 条消息中符合条件的来信写入当前账号的 `automation.json` → `accounts` → `replyQueue`，再按 `repliesPerRound` 分批处理。例如收到 10 条、每轮处理 5 条，其余 5 条会在下轮继续，不要求来信仍未读或仍在消息列表中。重启和关闭开关都保留队列；重新开启后继续。只有发现后的来信才受此保护，首次读取前已被新消息挤出最近 100 条范围的来信仍可能遗漏。

- 尚未处理、模型生成失败、暂时查不全评论关系、读取评论暂时失败、平台明确拒绝发送：保留队列，下一次允许的回复检查继续；优先处理尚未尝试或最久未尝试的来信，避免单条失败阻塞后续。
- 已发送或已受理：移出队列并保留去重；模型主动跳过、确认不是对自己的回复等不符合条件的来信也结束处理。
- 网络超时等发送结果未知：保留为「待确认」，不自动重发。请先到平台核对，当前没有自动核验或强制重发入口，避免重复评论。
- 每次实际发送尝试均计入每日额度，包括平台拒绝和未知结果；生成失败不扣发送额度。额度用尽时保留队列，按调度时区到次日后继续。登录失效或人机验证仍需处理后恢复，队列不能绕过平台限制。

在「概览」查看待处理 / 待确认数量，在「评论记录 → 待回复队列」查看来信 ID、帖子链接、尝试次数及最近失败原因，最多展示前 50 条。状态随界面每 5 秒刷新；原因经过凭据过滤。队列按账号隔离，仍仅写入小黑盒自己的数据目录，不操作 B 站历史。升级不会将旧版未入队的拒绝记录批量补发。

0.10.8 起，楼中楼查找每轮最多 5 页，未查完的游标保存在队列条目的 `scanCursor` 中，下轮继续，重启也保留。此前每轮从头查前 5 页，会漏掉更深的来信。查到底、分页无进展或找到目标时清除游标；未找到的来信仍留在队列，后续重新查找。帖子首页之外的根评论、删除或不可见的评论仍可能无法核对完整关系，此时不会贸然发送。

## 每日额度（0.10.9）

`dailyComments` 与 `dailyReplies` 分别设置每日评论和回复额度，范围为 0–9999 的整数，默认各为 10，0 表示没有发送额度。升级保留已有值，不会自动提高发送量。每次发送尝试均占额度，包括平台拒绝或结果未知；生成失败不扣额度。按配置时区跨日重新统计，冷却、运行时段和平台限制仍然生效。

## 独立人格定时发帖（0.11.0）

「发帖」Tab 配置文字新帖，默认关闭。搜索选择目标分区及话题标签（0.11.1），填写独立发帖人格和写作主题，再选择单次、每天或每周时间；保存时绑定当前账号。单次日期和周期时间按 `timeZone` 解释，与浏览调度共用时区；不受浏览峰谷时段限制。每周使用 1–7 表示周一至周日。DSH 宿主必须在线，关闭浏览器不会停止任务。

发帖使用高级设置中的 DSH / 第三方 Chat Completions 模型、超时和命令配置，但人格只取 `postingPersona`，不会回退到通用人格或回复人格。`postingPrompt` 是每次生成的主题与要求。模型返回 send / skip、标题（1–30 字）和纯文本正文（1–10000 字），宿主校验后发布；模型不能调用工具。首版不支持本地图片、搜图或视频。

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| postingEnabled | false | 发帖开关；通过设置页开启时绑定账号 |
| postingPersona | 内置独立发帖人格 | 最多 20000 字符，支持完整多行角色卡；开启时不能为空 |
| postingPrompt | 游戏话题讨论 | 最多 4000 字，开启时不能为空 |
| postingCommunities | [] | 最多 2 个分区，格式 `{ "id": "社区数字 ID", "name": "分区名称" }`；按 ID 去重 |
| postingHashtags | [] | 最多 5 个话题，格式 `{ "name": "标签名称", "isActivity": false }`；名称去重，活动话题最多 1 个 |
| postingTopicId | 空字符串 | 兼容旧版手填社区 ID；与 postingCommunities 二选一，开启时必须有目标分区 |
| postingTimingMode | fixed | fixed 固定时间 / prompt 提示词时间规划 |
| postingTimingPrompt | 每天 10–22 点选一个不固定时间 | 最多 2000 字；prompt 开启时不能为空 |
| postingDailyLimit | 1 | prompt 模式每日任务上限，1–10 |
| postingMinGapMinutes | 60 | prompt 模式最短间隔，10–1440 分钟 |
| postingSchedule | daily | once / daily / weekly |
| postingTime | 20:00 | 周期任务的 HH:mm 时间 |
| postingAt | 空字符串 | 单次任务的 YYYY-MM-DDTHH:mm 日期时间 |
| postingWeekdays | [1,2,3,4,5,6,7] | weekly 生效，至少选择一天 |

在「发帖分区与话题」输入名称后点击查询，分别点击分区或话题添加，点击已选项移除，再保存。留空查询读取平台推荐；需要先登录小黑盒。选择分区时自动清空旧版 ID；清空全部分区且未填写旧 ID 时，不能开启发帖。话题可不选，清空后发布不带话题标签。分区决定发布位置，话题标签用于分类，`postingPrompt` 决定写什么，三者分别配置。平台仍可能因权限、失效话题或活动要求拒绝发布。

配置文件示例（保存后按既有方式开启计划）：

```json
{
  "postingCommunities": [{ "id": "7214", "name": "示例分区，请以平台搜索结果为准" }],
  "postingHashtags": [{ "name": "示例话题，请以平台搜索结果为准", "isActivity": false }],
  "postingTopicId": ""
}
```

查询使用官方编辑器的 `/bbs/app/api/post_editor/topic_selection/index` 与 `/search`；宿主通过只读 `GET /heybox/posting-selections?q=关键词` 返回精简结果。社区提交为 `topic_ids`（逗号分隔 ID），话题提交为 `hashtags`（名称 JSON 数组）。手动模式下，模型只能生成标题和正文，不能改变发布目标。

发帖和浏览 / 回复串行执行，共用发送冷却；已在运行的任务可能延迟发布。宿主约每 5 秒检查，到期后生成内容。首次配置周期任务从未来一个时间点开始，不立即补发。超过计划时刻 10 分钟才轮到处理的任务标记 missed，不批量补发；单次任务结束后不重复执行。夏令时不存在的周期时间跳过，重复时刻只执行第一次；不存在的单次时间拒绝保存。

发帖状态保存在 `automation.json` 的账号独立 posting.jobs 中；人格、写作主题和选择设置在任务首次处理时固定；手动模式同时固定分区及话题，AI 模式在候选选择成功后固定发布目标；旧任务沿用原社区 ID。生成失败每分钟最多重试一次，最多尝试 3 次；重启保留未发送任务。保存过发送意图后，网络错误、缺少帖子 ID 或进程退出均视为待确认，不自动重发。平台明确拒绝则记为 rejected，本时间槽不重试。模型 skip 结束本次任务。

accepted 表示平台成功响应且返回帖子 ID；verified 表示进一步读取到相同 ID、标题和正文，都不保证其他账号可见或已经通过审核。每个时间槽只提交一次。切换账号不会把原账号计划交给新账号执行；如需绑定新账号，在该账号下重新保存开启发帖。停止全部任务会关闭发帖并取消尚未发送的生成；已经提交的请求无法撤回。

修改配置文件后仍需通过设置页开启以绑定账号；任务记录不含 Cookie 或 API Key。此版本没有真实账号公开发布验收，接口签名和实际社区权限需另行联调；不得把模拟测试视为公开发布已验证。


## 提示词时间规划（0.12.0）

推荐使用“每日模型规划 + 宿主定时执行”：模型根据时间提示词输出当天时间数组，宿主保存计划并在到期时唤醒模型生成正文。相比每隔几分钟问模型要不要发帖，这种方式调用更少、时间可查看、重启可恢复，且宿主能校验上限和间隔。插件不向模型开放任意任务工具，不依赖模型在后台等待。

在「发帖」选择「提示词规划时间」，填写时间提示词，设置每日上限、最短间隔，选择分区和话题，设置独立人格及内容主题，然后开启并保存。示例：

```json
{
  "postingTimingMode": "prompt",
  "postingTimingPrompt": "每天发 1–2 条，安排在 12:00–14:00 或 19:00–22:00，每天的时间不固定，周日不发。今天剩余时间不合适就不发。",
  "postingDailyLimit": 2,
  "postingMinGapMinutes": 120
}
```

两类提示词各司其职：`postingTimingPrompt` 决定何时发，`postingPrompt` 决定写什么；正文继续使用 `postingPersona`，分区 / 话题继续由宿主配置。规划与正文均使用高级设置选择的 DSH 或第三方 API，模型只输出 JSON，工具仍禁止。每天首次开启 / 登录后首次检查，以及宿主恢复后首次检查，会规划当天剩余时间；正常跨天后规划新一天。输入包含当前日期、时区、最早可用时间、当天既有任务、最多 7 次历史计划，以便安排变化的时刻。模型可以返回空数组，表示今天不发，不会因空计划反复请求。

宿主约每 5 秒检查一次本地计划，不调用模型。正常一天调用一次规划，再为每个到期帖子调用一次正文生成；失败重试会增加调用。宿主不在线时无法执行。未开始的昨日计划不会补发；当天超过计划 10 分钟的任务记为错过。生成或冷却期间跨天则不提交昨日帖子。

宿主强制校验：仅接受当天、至少一分钟以后的有效 HH:mm 时间，数量不能超过当天剩余名额，时间不可重复或过密；发送前另按实际发送时刻遵守最短间隔和共用冷却。规划失败或非法输出，至少 5 分钟后重试，最多 3 次，连续中断也计入次数；当日失败后不自动回退固定时间或重新规划。发送结果未知仍不自动重发。

每日上限指当天发帖任务数量，模型 skip、错过、生成失败、平台拒绝或发送待确认均占名额，避免不断补充产生额外任务。已有固定时间任务也计入切换到 prompt 时的当天预算。降低上限会跳过超出部分；增大间隔可能使计划延迟，延迟超过 10 分钟则错过。提示词里的“周日不发”“只在午休”等自然语言条件由模型理解，不能视为宿主已实现对应的硬性时段规则；需要严格固定时间可选原固定模式。模型选择有变化的时间，不承诺数学随机分布。

计划按账号和“时区 + 当地日期”存入 `automation.json` 的 posting.plans，最多保留 30 次；设置页展示最近 14 次。正常重启、关闭再开启、修改提示词不会重新抽取当天计划；新提示词用于下一天。每日上限和实际发送间隔即时约束剩余任务。修改时区会按新时区日期规划，切换回同一账号 / 时区 / 日期复用原计划。原固定时间配置保留，仅在 fixed 模式生效。发帖仍不受浏览峰谷时段限制，且与浏览 / 回复共用执行锁，因此到期执行可能延迟。

当前通过模拟时间和接口测试，尚无真实账号公开发布验收。公开发布权限、审核结果仍由平台决定。


## 回复自己帖子的评论（0.12.1）

入口：「互动 → 回复来信」。同时开启「自动回复评论」和「自动回复自己帖子的评论」，保存后使用现有消息检查间隔运行。不要求打开定时发帖或定时浏览；也适用于当前账号在 App 手动发布的帖子。仅根据消息接口发现来信，不定期扫描所有历史帖子。保持原消息新鲜度规则：明确未读可包含旧消息，没有可靠读状态时要求启用后的时间戳。

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| replyOwnPosts | false | 允许回复自己帖子下其他用户直接发表的顶层评论；需 autoReply=true |
| ownPostReplyPersona | reply | reply 使用回复人格（留空回退通用）；posting 沿用发帖人格 |

宿主读取帖子详情核实作者，并确认来信评论 / 根评论关系。顶层评论以自己的评论 ID 作为 root_id，回复目标为对方该条评论 ID。消息缺少 root_comment_id 或返回 0 时，先从详情确定根评论；不会凭通知猜测归属。较旧顶层评论按帖子评论列表分页查找，每轮最多多查 5 页并保存进度。缺失作者、评论或父子关系时保留到下轮；自己发表的评论和已确认不是在回复自己的其他用户对话不回复。

选择 posting 时，优先使用该帖对应的 accepted / verified 发帖任务中的人格快照；记录已清理或属于手动帖子时，使用当前 postingPersona，并要求该人格非空。对自己帖子的顶层评论及后续明确回复自己的评论都使用该选择。其他帖子里回复自己的评论仍使用 replyPersona，留空回退 persona。DSH 与第三方 API 走相同人格注入；模型仍可选择 skip。

共用 repliesPerRound、dailyReplies、发送冷却、运行时段选择和按账号的 replyQueue / actions 去重。超出本轮数量或每日额度保留；生成失败、平台明确拒绝下轮重试；发送结果未知不重发。关闭 replyOwnPosts 后，已发现的自己帖子顶层评论保留为等待开启，已识别的等待项不会继续占每轮处理名额；其他直接回复自己的评论继续按 autoReply 处理。关闭 autoReply 停止整个回复检查，进行中的生成结果不再发送。

「评论记录」区分“回复自己帖子的评论”并显示人格来源。不保证每条都能回复：仍受消息接口可见范围、删除评论、账号权限、平台限制、模型 skip 和发送结果未知影响。旧版本已经永久标记 skipped 的来信不会自动重置，避免误恢复曾明确忽略的消息。本次仅通过模拟测试，未发送真实账号回复。


## AI 自动选择分区与话题（0.12.2）

入口：「发帖 → 发帖分区与话题 → 分区与话题选择方式 → AI 自动选择」。不必预先手选分区，仍需填写独立发帖人格、发帖主题并配置发布时间、登录账号和模型。

- **AI 候选搜索词**：选填，最多 100 字。留空使用平台推荐；填写例如“单机游戏”，则使用该关键词的官方搜索结果。该词由用户设置，模型不会自行扩展搜索或遍历全部社区。
- **AI 分区与话题选择偏好**：选填，最多 2000 字，例如“优先讨论游戏设计，避免无关活动话题”。模型结合偏好、发帖主题和独立发帖人格选择目标。
- 每次到期先查询平台候选，模型选择 1–2 个分区、0–5 个话题，活动话题最多 1 个，再按选中目标生成正文。只允许候选中的 ID 和名称，不能编造。候选不代表账号一定有发帖权限。
- 推荐 / 搜索结果为空或模型判断没有合适分区时，本次跳过。查询失败或选择结果无效时按现有任务策略重试，最多 3 次，不回退手动目标或其他分区。
- 本模式保留手动选择供切回使用，但不参与新任务发布。模式、搜索词、偏好、主题与人格在任务首次处理时保存；目标选择成功后固定，生成正文失败或重启不会重新选择。修改设置对已开始任务不生效。
- 「发帖记录」显示 AI 选择标记与最终分区、话题。发送结果未知仍不自动重发。默认保持手动模式，升级不会自动切换或开启发帖。

```json
{
  "postingSelectionMode": "ai",
  "postingSelectionQuery": "单机游戏",
  "postingSelectionPrompt": "优先游戏设计讨论，话题仅选与内容相关的普通话题"
}
```

DSH 与第三方 API 均使用高级设置中的模型，选择阶段与正文生成阶段均注入独立发帖人格。相较手动模式，每次首次选区增加一次候选查询和一次模型请求；模型接收候选名称与分区 ID，不接收 Cookie / API 密钥。该能力可与固定时间或提示词规划时间组合使用。真实账号发帖权限、平台接受及公开可见性仍需验收。
